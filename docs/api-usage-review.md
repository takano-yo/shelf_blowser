# API 取得手法のレビュー（v1.0 公開前チェック）

> **目的**: version 1.0 として公開する前に、開発過程で行った外部 API 取得が
> 各 API の利用条件・アクセス頻度の要件に適合していたかを点検する。
> **対象**: CiNii Books OpenSearch / openBD / JLA NDC-LD（ndc9.zip）。
> **実施日**: 2026-08-05。

## 結論（要約）

- **アクセス頻度・負荷の面では問題なし。** NDC 一覧取得の実測は
  **1,110 リクエスト / 72.6 分・中央値 4.0 秒間隔・最小間隔 1.0 秒・60 秒あたり最大 25 件**で、
  直列・1 秒以上の間隔が全リクエストで守られていた（下記「実測」）。
- **一方、CiNii の必須パラメータ `appid` を送っていなかった。** 公式仕様上
  `appid` は **必須**であり、これは頻度ではなく**利用登録の要件**に対する不適合。
  **v1.0 公開前に対応が必要な唯一の必須項目**。
- そのほかは「仕様外の値への依存（`count=10000`）」「エラー時の再試行が
  雑（403 でも叩き直す）」「openBD の一時失敗が恒久キャッシュされる」など、
  公開前に直しておきたい項目が数点。**取得済みデータそのものに毀損はない**。

---

## 検証方法

推測ではなく、リポジトリに残っている実データから実際の取得挙動を再構成した。

- `site/data/ndc/index.json` の各分類の `fetchedAt` は **CiNii のレスポンス生成時刻
  （`dc:date`）** なので、これを並べると実際のリクエスト時刻列がそのまま得られる。
- 書影の充足率は `site/data/ndc/*.json` 全 936,548 レコードを走査して集計。
- 仮説（ISBN-10 のまま問い合わせて取りこぼしていないか）は openBD へ
  少量（30 件 × 2 回）の実リクエストで検証した。
- 各 API の要件は公式ドキュメントを参照（末尾「参照した一次情報」）。

## ① CiNii Books OpenSearch

### 実測: 取得頻度・件数

`index.json` の `fetchedAt` 1,110 件から再構成した実績。

| 指標 | 実測値 |
|---|---|
| リクエスト数（一覧取得） | 1,110 |
| 期間 | 2026-07-14 14:03:28 〜 15:16:06（JST） |
| 総所要 | 72.6 分 |
| 平均間隔 | 3.93 秒 |
| 間隔の中央値 / 最小 / 最大 | 4.00 秒 / **1.00 秒** / 29.00 秒 |
| **1 秒未満の間隔** | **0 件** |
| 60 秒あたり最大リクエスト数 | 25 |
| 間隔の分布 | 1〜2 秒: 3 / 2〜5 秒: 929 / 5〜30 秒: 177 |

これに件数実測モード（`--counts`、`count=1` の軽量コール）1,110 件と
パイロットの `source/0.json` を加え、**開発過程での CiNii への総リクエスト数は
約 2,221 件**。受信レコードは延べ約 168 万件（ランブックの `--count 2000` 前提で
約 0.7GB）。

**評価**: CiNii の要件は「他の利用者に影響を与えるような短時間で大量のアクセスを
行わないこと」という定性的なもので、定量的な上限は公開されていない。
実測の 25 件/分・最小間隔 1 秒・完全直列は、この要件に対して**十分に保守的**。
1 回きりの初期整備であり、頻度・総量とも問題は認められない。

設計面でも、CiNii へのマナーとして挙げられている項目は実装済みだった。

- 直列取得（並列化なし）／リクエスト間隔（既定 1.0 秒、実運用は約 4 秒）
- 指数バックオフ（2→4→8→16 秒）
- 取得済みスキップによる冪等・中断再開（無駄な再取得をしない）
- 失敗分類を `failed.txt` に記録し、再実行で失敗分のみ再試行

### 🔴 問題 1（必須対応）: `appid` を送っていない

CiNii Books OpenSearch の公式仕様では、リクエストパラメータのうち **`appid` だけが
「必須です」と明記**されている（他は全て任意）。開発者登録ページでも
「OpenSearch, RDF などの API を利用される方は…アプリケーション ID を取得してください」
とされている。

しかし `core/ciniisearch.py` の `build_opensearch_url()` は `q` / `clas` / `format` /
`count` / `sortorder` / `type` / `gmd` しか組み立てておらず、**`appid` を一切送っていない**。
つまり上記 約 2,221 リクエストすべてが未登録・`appid` 無しで実行された。

原因は仕様理解の齟齬にある。`core/README.md` は CiNii Research への移行差分として

> **appid（アプリケーション ID）必須** — 現行は不要だった。

と書いており、ルート `README.md` も「新 API は appid 必須」と、**appid を移行後の
話として扱っている**。実際には現行の CiNii Books OpenSearch でも必須。

補強材料として、`fetch/README.md` のランブックには

> 共有 IP 等で断続的に 403〈Access Limit Over〉が出る場合も、再実行すれば失敗分だけ再試行される

という記述がある。**実際に遮断を受けた形跡**であり、`appid` 無しの匿名アクセスに
対して厳しめの枠が適用されていた可能性が高い。

**対応**: v1.0 公開前に API 利用登録を行い、`appid` を環境変数（例 `CINII_APPID`）
から読んでパラメータに追加する。公開サイトから利用する構成なので、登録時に
用途を申告しておく（商用利用等は事前連絡が求められている）。

### 🟠 問題 2: `count=10000` は仕様に保証されていない値

公式仕様の `count` の説明は「デフォルト 20」のみで、**上限の記載がない**。
ページングは `p`（ページ番号）で行う仕様。

`source/0.json` を見ると `itemsPerPage: 10000` / `items` 10,000 件で実際に返っており、
動作自体はしている。ただしこれは**仕様に書かれていない挙動への依存**で、
サーバ側の設定変更でいつ壊れてもおかしくない。CiNii Research 移行後は
200 件/コール上限になることが既に判明しており、いずれにせよページング実装が要る。

あわせて、**コードの既定値とランブックの推奨値がずれている**。

- `fetch/ndc_fetch.py:164` … `--count` の既定は **10000**
- `fetch/README.md` のランブック … `--count 2000` を推奨（「転送量・CiNii への負荷を減らせる」）
- `server/app.py` の `CONFIG["count"]` … **10000**

保存上限（`--ndc-max`）は 1,000 件に確定しているので、10,000 件取得は
**9 割が捨てられる転送**になる。既定値を実際の運用値（2,000）に合わせるべき。

### 🟠 問題 3: HTTP ステータスを区別せず再試行している

`core/ciniisearch.py:98` の再試行は `except Exception` で、HTTP エラーを区別しない。

```python
except Exception:  # noqa: BLE001 — リトライ対象を広く取る
    if attempt == retries - 1:
        raise
    time.sleep(delay)
    delay *= 2
```

このため **403（Access Limit Over＝遮断中）でも 2/4/8/16 秒で 4 回叩き直す**。
遮断されている相手に叩き足す挙動で、マナーとしては逆効果。
400（パラメータ不正）も同様に 4 回無駄打ちになる。

**対応**: `urllib.error.HTTPError` を捕捉して、4xx（429 を除く）は即座に失敗、
403/429 は `Retry-After` を尊重するか大きめの待機（分単位）に切り替える。

### 🟡 問題 4: 上位階層 110 分類の取得は不要だった

`clas=<記号>*` の前方一致で 類（1 桁）10・綱（2 桁）100・目（3 桁）1,000 を
それぞれ取得しているが、上位階層は下位階層の和集合に完全に含まれる。実測:

| 検証 | 親の件数 | 子の和集合 | 親にあって子に無い NCID |
|---|---|---|---|
| 綱 `91` vs 目 `910`〜`919` | 1,000 | 9,627 | **0（0.0%）** |
| 類 `9` vs 綱 `90`〜`99` | 1,000 | 9,929 | **0（0.0%）** |

理論的にもこうなる。所蔵館数上位 1,000 件を採るとき、親の上位 1,000 件に入る
書誌は、自分が属する子分類の中では高々 999 件しか上位に居ないので、
必ず子分類の上位 1,000 件にも入る。

**対応（次回の再取得時）**: 目 1,000 分類だけ取得し、類・綱はローカルで導出すれば
**CiNii へのリクエストを約 10% 削減**できる。
（厳密には「NDC が 1〜2 桁で止まる書誌」があると欠落しうるが、実測では 0 件）

### 🟡 問題 5: User-Agent の連絡先がプレースホルダのまま

```python
# 連絡先を含む明示的な UA（CiNii へのマナー）。運用時は連絡先を差し替える。
USER_AGENT = "shelf_blowser/0.1 (+https://github.com/takano-yo/shelf_blowser)"
```

コメント自身が「運用時は差し替える」と言っており、v1.0 では確定させたい。
リポジトリ URL のみで連絡先メールが無いので、遮断時に CiNii 側から連絡が取れない。

### 🟡 問題 6: `server/app.py` を公開する場合のレート制御が無い

現在は「検証用のローカル起動」なので実害は出ていないが、v1.0 で公開ホストに
置くなら、以下がそのまま**無制限の CiNii 中継**になる。

- `ThreadingHTTPServer` … 同時リクエスト数の制限なし。複数ユーザーの検索が
  そのまま**並行して** CiNii へ飛ぶ（バッチ側で守っている「直列取得」が崩れる）
- CiNii 呼び出しにリクエスト間隔・レート制限が**一切ない**
- 1 検索 = `count=10000`（約 4MB）の重いリクエスト
- `Access-Control-Allow-Origin: *` … 任意のサイトから叩ける
- 緩和材料: 検索語ごとの結果キャッシュ（既定 TTL 1 時間）はある

**対応（公開する場合のみ）**: CiNii 呼び出しをプロセス内で直列化＋最小間隔を強制、
`count` の既定を 200〜1,000 程度に引き下げ、クライアント単位のレート制限を入れる。
公開しない（GitHub Pages の静的配信のみで v1.0 とする）なら現状のままでよい。

### ✅ 適合していた点

- `clas` の前方一致（`clas=0*`）・`sortorder=5`（所蔵館数降順）・`type` / `gmd` /
  `format=json` は、いずれも**公式仕様に存在するパラメータ**を正しい値で使用している。
- 出典表示: CiNii Books のメタデータは CC BY 4.0 で公開されており、
  `site/shelf.html` のフッタと概要、`index.json` の `dataSource` で
  出典・ライセンスを明示している。**CC BY の帰属要件を満たしている**。
- ブラウザから CiNii を直接叩いていない（`site/js/*.js` の `fetch()` は
  自 API と同一オリジンの静的ファイルのみ）。
- GitHub Actions（`.github/workflows/pages.yml`）は外部 API を呼ばない
  （検索コーパスを `site/data/ndc/` からローカル生成するだけ）。CI が
  意図せず API を叩き続ける事故は起こらない構成。

## ② openBD

### 実測

- 対象: 一意 ISBN **547,945 件** → `batch=1000` で **約 548 リクエスト**、間隔 1.0 秒。
- 総レコード 936,548 のうち ISBN あり 693,792（74.1%）、`coverUrl` あり 32,572。
- 頻度・件数とも過大ではない。openBD は定量的なレート制限を公表していないが、
  ISBN 単位のファイルキャッシュ（`.cache/openbd/`）で再取得を避ける設計になっており、
  `build` と `server` でキャッシュを共有する点も含めて無駄打ちが少ない。

### 🟠 問題 7: 一時的な取得失敗が「書影なし」として恒久キャッシュされる

`core/openbd.py:87-96`:

```python
data = _http_get_json(url, retries)
if data is None:                      # ← 4 回リトライしても失敗した場合
    data = [None] * len(chunk)
for isbn, entry in zip(chunk, data):
    ...
    rec = {"coverUrl": cover}         # ← None が入る
    cache_mem[isbn] = rec
    _write_json_atomic(cache_path(isbn), rec)   # ← 恒久キャッシュに書き込む
```

`_http_get_json` はリトライ尽きても例外を投げず `None` を返す設計なので、
**ネットワーク一時障害が「この ISBN に書影は無い」という確定結果として
ディスクに記録される**。以降 `p.exists()` が真になるため二度と再取得されない。
`batch=1000` なので、**1 回の失敗で 1,000 ISBN が恒久的に欠損**する。

**対応**: 取得失敗時はキャッシュを書かない（`pending` に残す）。
既存キャッシュの救済は、失敗が起きたかどうかログが残っていないため、
気になるなら `coverUrl: null` のキャッシュだけ削除して再実行すればよい。

### 書影充足率の低さは不具合ではない（検証済み）

ISBN ありレコードのうち書影が付いたのは 4.7%。桁数別では

| ISBN 桁数 | 件数 | 書影あり |
|---|---|---|
| 10 桁 | 439,910 | 7,663（1.7%） |
| 13 桁 | 253,882 | 24,909（9.8%） |

この約 6 倍の差から「ISBN-10 のまま問い合わせて openBD が引けていないのでは」
という仮説を立て、**openBD へ実際に問い合わせて検証した**（書影の付かなかった
ISBN-10 を 30 件サンプル）。

- ISBN-10 のまま … 30 件中 **26 件が該当**（書誌は返る）、うち書影 0 件
- ISBN-13 に変換 … 30 件中 **26 件が該当**、うち書影 0 件

**結果は同一**。openBD は ISBN-10 でも正しく引けており、キー不整合ではない。
充足率の低さは、CiNii Books の蔵書が古く openBD（近刊・現行本の販促データが中心）に
書影が無いことが原因。**取得手法の問題ではない**。

### 🟡 問題 8: UA に連絡先が無い / `batch=1000` の GET が仕様外依存

- `core/openbd.py:34` の UA は `"shelf_blowser/0.1"` のみで、CiNii 側（URL 入り）と
  不揃い。同じ UA 方針に揃えたい。
- `batch=1000` は GET のクエリ文字列が約 14KB になる。openBD の公開ドキュメントには
  1 リクエストあたりの ISBN 数上限の明記が無く、大量指定は POST が案内されることが多い。
  現に動作しているが、`count=10000` と同じく仕様外依存。

### 利用目的の適合

openBD の利用規約は「本の販促・紹介目的に限り使用できます。個人・団体・企業を
問いません」「取得データを任意に改変してはいけません」と定める。
本アプリは書誌の紹介・ブラウジング用途で、書影 URL はそのまま `<img src>` で
参照している（改変なし）ため、規約の範囲内と読める。
`site/shelf.html` フッタに「表紙画像: openBD」の出典表示もある。

なお openBD 旧 API（v1）は 2023 年 7 月に提供終了が告知されており、
ルート README も認識済み。書影のフォールバック整備（NDL サムネイル API 等）は
ロードマップ項目として残っている。

## ③ JLA NDC-LD（`fetch/ndc_labels.py`）

**問題なし。**

- `ndc9.zip` を **1 回だけ**取得し、`.cache/ndc/ndc9.zip` にキャッシュ、
  取得済みならスキップ（`download_zip`）。`labels.json` も生成済みならスキップ。
  → 繰り返しアクセスが構造的に起きない。
- CiNii と同じ UA を付けている。
- ライセンス: JLA が NDC 新訂 9 版データを **CC BY** で公式公開しており、
  `labels.json` の `source`（発行者・URL・ライセンス・取得日）を `index.json` の
  `labelSource` に引き継ぎ、スタートページ（`site/index.html`）に
  「出典 : 日本図書館協会 NDC-LD NDC9版（CC BY ライセンス）」として表示している。
  **帰属要件を満たしている**。
- NDC Navi（NDC10 版）を使わず CC BY の公式データを選んだ判断も適切
  （NDC Navi は第三者向け利用規約が未公開）。
